# MarginHash

MarginHash приводит разрозненные предложения ASIC-майнеров от продавцов, работающих на российском рынке, к сопоставимому каталогу и сохраняет историю цен. Я разработал адаптеры источников, сбор и сопоставление предложений, расчёт сценарной доходности и Flask-приложение для показа результатов. В закрытой кодовой базе зарегистрировано 20 адаптеров. Это количество настроенных интеграций, а не утверждение, что все 20 продавцов сейчас доступны в production.

Главная инженерная задача — сохранить связь между конкретным предложением и его характеристиками, когда сайты по-разному называют модели, указывают единицы измерения, наличие и спецификации. Цена, хешрейт, мощность и расчётная доходность в карточке модели должны относиться к одному совместимому предложению.

Этот публичный репозиторий содержит только техническое описание. Исходный код приложения, cache продавцов, история цен и конфигурация сервера закрыты. Ниже описана локальная версия кода, изученная 1 ноября 2026 года; актуальное состояние production отдельно не подтверждалось.

## Схема системы

~~~mermaid
flowchart LR
    Sites[Сайты продавцов] --> Adapters[Адаптеры источников]
    Adapters --> Cache[Cache по источникам]
    Cache --> Merge[Нормализация и сопоставление]
    Merge --> ASIC[(SQLite: ASIC и предложения)]
    ASIC --> Builder[Сборка read model]
    Builder --> Snapshots[Версионированные JSON snapshots]
    Snapshots --> Web[Страницы и API Flask]
    Web --> Browser[Каталог и графики на JavaScript]
    Merge --> History[(SQLite: история цен)]
    History --> Web
    Rates[Сетевые показатели и курс валют] --> Builder
~~~

Планировщик запускает группы парсеров и сборку read model вне обработки веб-запросов. Отдельный runtime boundary передаёт команды и подготовленные файлы между фоновыми задачами и Flask. Веб-процесс обычно читает snapshots; для части данных в коде остаются legacy fallback-маршруты.

## Сбор данных

Реестр источников распределяет 20 адаптеров по трём группам. Каждый адаптер учитывает структуру сайта продавца и возвращает предложение в общей форме: модель, хешрейт и его единица, мощность, цена, наличие, источник и прямая ссылка. Способ извлечения зависит от сайта:

- MiningMoon использует JSON API WooCommerce.
- MineStream читает AJAX-фрагменты, с fallback на HTML.
- Geometria при необходимости переходит от прямого HTTP-запроса к автоматизации браузера.
- PushMiner сопоставляет HTML каталога с Product/Offer JSON-LD и сохраняет ссылку на конкретный вариант предложения.

Rate limiter задаёт интервалы отдельно для источника и режима запроса. Runtime парсеров учитывает ошибки и паузы перед повторной попыткой. Fallback на cache существует, но не каждый адаптер явно помечает такой результат как устаревший. Поэтому наличие записи в cache само по себе не доказывает актуальность предложения. Подробнее: [сбор и нормализация данных](docs/engineering/DATA_PIPELINE.md).

## Нормализация и read model

Слой объединения переводит валюты и единицы хешрейта, отбрасывает непригодные записи, дополняет недостающие характеристики из совместимых источников и сохраняет предложения отдельных продавцов. При нечётком сопоставлении требуется точное совпадение токена модели: S21 не смешивается с S21e. Варианты air, hydro и immersion проверяются отдельно. Это сопоставление по правилам, а не свободное объединение похожих названий.

Сборщик read model удаляет точные дубли и записи не о майнерах, помечает восстановленную мощность и исключает подозрительные ценовые выбросы из расчёта цены, сохраняя саму запись. Группировка разделяет несовместимые варианты и выбирает предложение для карточки модели. Подозрительные характеристики группы заменяются только при подтверждении от независимых источников. Иначе можно было бы показать цену одного варианта, а хешрейт и доходность другого. Подробнее: [правила сопоставления](docs/engineering/DATA_PIPELINE.md).

## Расчёты и история цен

Расчёт дневной чистой выручки использует доходность на единицу хешрейта, комиссии пула и P2P, мощность и тариф на электричество:

~~~text
net_RUB_per_day = rate_RUB_per_unit_day * hashrate * (1 - pool_fee) * (1 - P2P_fee)
                  - power_kW * 24 * electricity_RUB_per_kWh
~~~

Обновление ставки использует сетевые данные WhatToMine и курс USD/RUB. Длинный сценарий суммирует дневные результаты до фиксированной в текущем коде даты халвинга, учитывает ежегодное изменение тарифа и показывает базовый сценарий, а также варианты с выручкой +20% и −20%. Окупаемость — первый день, когда накопленная чистая выручка достигает цены выбранного предложения. Это сценарные оценки, а не прогноз дохода.

Локальное хранилище истории цен использует SQLite WAL. Оно записывает изменения и периодические подтверждения неизменной цены, обновляет ревизию истории в той же транзакции и отдаёт данные через cache с учётом версии. Старый JSON служит источником для явного legacy-импорта, а не обычным путём чтения. Миграция production **не проверена**. Подробнее: [расчёты и история цен](docs/engineering/ANALYTICS.md).

## Веб-приложение и эксплуатация

Backend написан на Python, Flask и Gunicorn; также используются sqlite3, requests и Beautiful Soup. HTML формируется на сервере и дополняется JavaScript. Страница модели загружает Chart.js по необходимости. Каталог получает подготовленный JSON для поиска, фильтрации и сортировки в браузере. Endpoint каталога использует версионированный payload и HTTP cache headers, а история кэшируется по версии данных и выбранному периоду. Часть API-маршрутов внутренняя или защищённая, поэтому это не открытый API без ограничений.

Подготовленные snapshots и ограниченные по размеру cache в памяти уменьшают повторную работу в запросах. В закрытой кодовой базе есть конфигурации Nginx и systemd и реализация поэтапного deploy. Наличие этих файлов не доказывает измеренную пропускную способность или выкатку последних локальных изменений. На момент проверки в закрытом checkout не было конфигурации CI. Подробнее: [архитектура и ограничения](docs/engineering/ARCHITECTURE.md).

| Сбор данных | source/, parser_runtime.py, scheduler.py |

Тесты охватывают согласованность модели и предложения, допущения расчётов, группировку, snapshots, историю цен и ошибки отдельных парсеров. При подготовке документации под Python 3.13 прошли 20 тестов из четырёх выбранных модулей с отключённым фоновым запуском. Это не проверка всего набора тестов и не валидация production. Внутренний аудит связывает эти утверждения с кодом; в публичный репозиторий он не входит.

Описание относится к локальному коду на 1 ноября 2026 года. Оно не утверждает, что данные production свежие или что охвачен весь рынок. Рыночные доли поставщиков и отклонение цен от медианы модели пока остаются идеями, а не реализованными метриками.
