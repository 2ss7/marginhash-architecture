# Как устроен MarginHash

MarginHash объединяет каталог ASIC, историю цен и расчётные показатели в одном веб-сервисе. Сбор предложений и подготовка данных работают отдельно от показа страниц: пользователь открывает готовый каталог, а не ждёт, пока сайт обойдёт магазины и пересчитает все модели.

## Путь от магазина до страницы

~~~text
сайты продавцов → сбор предложений → нормализация моделей → SQLite
                                              ↓
                                    подготовленные данные
                                              ↓
                                    веб-приложение → браузер
~~~

Планировщик обновляет предложения, историю цен и подготовленные данные каталога. Веб-приложение на Flask читает опубликованные результаты. Команды ручного обновления передаются планировщику через отдельную файловую границу; обычный HTTP-запрос не запускает парсер напрямую.

## Хранение и обновление

В SQLite хранятся нормализованные модели и предложения ASIC. История цен также использует SQLite: позиции связаны с точками изменения или удержания цены, что сокращает объём повторяющихся записей. Для неё старый JSON служит источником явного импорта. У части читателей каталога ещё есть JSON fallback, поэтому переход хранения на SQLite нельзя считать завершённым для всего проекта.

Cache отдельных магазинов, сетевые ставки и подготовленные данные разнесены по runtime-директориям. Данные для API публикуются атомарной заменой файла. Версия опубликованных данных помогает веб-процессам обновлять свой cache без пересборки каталога при каждом запросе.

## Скорость интерфейса

Каталог загружает подготовленные данные, затем выполняет поиск, фильтрацию и сортировку в браузере. Страница модели запрашивает график истории, когда он приближается к видимой области. API каталога использует ETag: при неизменной версии браузер может получить ответ 304 без повторной передачи данных.

Эти решения уменьшают работу во время обычного запроса. Подтверждённого публичного benchmark нагрузки пока нет, поэтому конкретные показатели скорости и отказоустойчивости здесь не заявлены.

## Что ещё требует внимания

Часть маршрутов сохраняет JSON fallback. Не каждый старый cache источника помечается как устаревший, а один из способов записи cache не атомарный. Timeout парсера прекращает ожидание, но может оставить его рабочий поток активным. Эти ограничения важны для контроля свежести данных и устойчивости обновления.
